# Event Log System

Scrolling event log. How the player learns what's happening in the simulation.

---

## Purpose

The player spends most of their time observing the map. But the map can't show everything -- it shows current state, not state changes. The event log is the primary communication channel between the simulation and the player, surfacing significant happenings as they occur.

This system is also the foundation of debugging tooling. The canonry's most useful end-user features emerged from systems built to debug simulation behavior. The same will likely be true here: the event log starts as a debugging aid and evolves into a player-facing feature.

---

## Design Decisions

### Scrolling log for MVP

A simple chronological list of event entries. Most recent at top. Scrollable. Filterable by entity kind, by event type, by region.

No popups, no pause-on-event, no priority system for MVP. Just a running record that the player can glance at. Post-MVP can add notification priority, map pings, pause-on-significant-event, and attention-directing features.

### Events are generated by all systems

Every system that modifies the entity graph in a significant way generates an event entry:

- **Generator executor:** "Settlement founded: Frosthollow, controlled by The Sovereignty of Kesh" 
- **Action executor:** "Nation declared war: Kesh vs. The Free Cities" / "Alliance formed: Kesh and the Shelf Compact"
- **System executor:** significant threshold crossings: "Cultural friction critical in the Northern Highlands"
- **Lifecycle:** "NPC died: Captain Thornfin (age 67)" / "Settlement abandoned: Old Waypoint (population 0)"
- **Relationships:** "Alliance dissolved: Kesh-Compact alliance strength reached 0"
- **Card tableau:** "Card activated: Cultural Diffusion" / "Card expired: Frontier Settlement"

### Events reference entities

Each event entry links to the entities involved. Clicking an entity name in the log navigates to that entity's detail panel. This makes the log an entry point for investigation: "I see a war was declared -- let me click on the nations involved to understand why."

### Event entries are brief

Events are one-line descriptions, not narratives. "War declared: Kesh vs Free Cities" not a paragraph about the geopolitical context. The log is for awareness, not storytelling. The player who wants to understand context clicks through to entity details.

### The log is the debugging backbone

During development, the event log serves double duty:
- Player-facing: awareness of simulation activity
- Developer-facing: tracing causality, understanding why the simulation behaved a certain way, identifying degenerate states

The log should support filtering, searching, and export from day one. Additional debugging views (card firing history, precondition evaluation traces, attribute change logs) can layer on top of the same infrastructure.

---

## Event Entry Structure

Each event has:
- **Tick:** when it happened
- **Type:** creation, destruction, relationship, conflict, diplomacy, lifecycle, card, threshold
- **Entities involved:** linked references to 1-N entities
- **Description:** brief text (template-generated from event type + entity names)
- **Source system:** which system generated this event (for debugging)

## Interactions with Other Systems

| System | How Event Log Interacts |
|--------|------------------------|
| All systems | Systems emit events when significant state changes occur |
| Entity Graph (#1) | Events reference entity IDs for linking |
| Save/Load (#15) | Event history is serialized (at least recent history; full history may be trimmed) |
| Map Visualization (#10) | Post-MVP: events may trigger map pings or animations |

---

## MVP Scope

Scrolling text log. Filterable by type and entity. Entity names are clickable links. Generated by all executor and lifecycle systems. No priority, no map integration, no pause-on-event. Serves as both player feature and debugging tool.
