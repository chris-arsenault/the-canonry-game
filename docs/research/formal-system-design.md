# Filtering simulation actions: a practitioner's methodological toolkit

**The core solution to your "cool but meaningless" action problem is a constraint-first, multi-phase design workflow that professional simulation designers converge on independently.** Rather than brainstorming actions and filtering down, the documented successful approach inverts the process: define invariants and resource flows first, derive the permissible action space from that structure, then use formal feedback-loop analysis to verify each action is load-bearing. This report synthesizes documented processes from Dwarf Fortress, Crusader Kings, Victoria, The Sims, RimWorld, and Civilization alongside formal modeling methodologies from agent-based modeling, system dynamics, and game AI architecture research. The workflow that emerges has six distinct phases, each with concrete tools and decision procedures.

## Start from stocks and flows, not from actions

The single most effective process shift documented across simulation designers is beginning with resource structure rather than agent behaviors. Will Wright built SimCity explicitly on Jay Forrester's system dynamics methodology: **"System dynamics is a way to look at a system and divide it into stocks and flows. Stocks are quantities, like population, and flows are rates, like the death rate, birth rate, immigration. You can model almost anything using those two features."** SimCity was a hybrid of Forrester's stock-and-flow models with cellular automata — the action space emerged from the flow structure, not the other way around.

The practical workflow proceeds in phases. **Phase 1** defines invariants as formal predicates over simulation state — conservation laws, boundedness constraints, anti-monopoly conditions. Trail of Bits' "Invariant-Driven Development" methodology (generalized from smart contract verification) prescribes identifying the 10 most essential invariants before any implementation and designing all subsequent logic to preserve them. For a procedural history simulation, these might include: total territory is conserved, population cannot go negative, no faction controls more than N% of a resource indefinitely without triggering countervailing pressure.

**Phase 2** builds a stock-and-flow model in Machinations, Vensim, or Insight Maker. Every resource type becomes a stock; every transfer mechanism becomes a flow with rate equations. Conservation is automatic in this formalism — a stock changes only via its defined inflows and outflows. Mikael Andersson's Victoria 3 economy redesign exemplifies this process: he identified three specific named failure modes in Victoria 2's circular economy (distribution modeling failures, substitution modeling failures, iterative imbalancing) and rebuilt the entire system as a snapshot-based open economy model where **"we turn the taps on full blast, letting all resources trickle through the system in an instant, using these quantities to assign prices... then wipe the slate clean and start over with no memory of the previous iteration."** The key constraint: the economic model must be predictable — if the player considers building a Textile Mill, the system can predict the price impact before construction begins.

**Phase 3** derives agent actions directly from the flow structure. Charles Macal's "Agency Theorem" (2006) proves that all well-formed system dynamics models can be translated into equivalent agent-based models through a rigorous procedure: each flow maps to one or more agent action types, flow rate constraints become action frequency constraints, and stock bounds become population-level invariants. Borshchev and Filippov at AnyLogic demonstrated the step-by-step translation: replace each stock compartment with a population of agents having state variables, replace aggregate flow rates with individual transition probabilities, and each agent action becomes the micro-level behavior that in aggregate reproduces the macro flow. **An action that has no corresponding flow in your stock-and-flow model has no structural role in the simulation — it is decorative by definition.**

## How studio designers actually filter mechanics

The documented design processes from major simulation studios reveal a convergent set of filtering heuristics, none of which start from brainstormed action lists.

Tarn Adams (Dwarf Fortress) uses what might be called "story-test driven development." His brother Zach writes target stories — narrative outcomes the simulation should be capable of producing — and Tarn builds systems capable of generating them. Systems that don't contribute to story generation don't make the priority list. Adams maintains a master feature list of roughly 2,600 planned features and uses a prerequisite identification method for ordering: when planning myth generation, he first identified artifacts as essential prerequisites and spent a year implementing them. The filtering question is not "is this feature cool?" but **"does this system change how existing systems work?"** When Z-levels were added, they "changed everything about fortress defenses, fortress layouts, how people thought to make rooms, how fluids worked."

Henrik Fåhraeus (Crusader Kings 2) discovered a different but complementary filter: find a single unified mechanic that everything connects through. For CK2, this was the Opinion system (-100 to +100). Every character trait, every action, every relationship resolves to opinion modifiers. The Seven Deadly Sins and Virtues were added because they mechanically create opinion-driven conflict — a Lustful duke is automatically wary of a Chaste queen. Fåhraeus articulated a critical distinction: **"I generally don't like to be surprised by the game mechanics; that means our design was too sketchy. There is a huge difference between unexpected (weird) and expected (reasonable) random outcomes."** His test for whether a system is working: beta testers don't talk about it. Well-functioning mechanics become invisible infrastructure.

Soren Johnson (Civilization IV, Old World) practices iterative subtraction across sequels — explicitly removing mechanics that proved ineffective in prior iterations. His documented insight from Civ III: resource scarcity "became a catalyst for the diplomacy system," demonstrating that a mechanic is load-bearing when it forces interaction between systems that would otherwise be independent. In Old World, he introduced the "orders" system specifically to make previously free actions costly, forcing meaningful trade-offs between military and economic activity. His process for identifying dead mechanics is observational: watch what players actually do versus what the game theoretically supports.

Tynan Sylvester (RimWorld) provides the most formalized filtering process. His "Ship-Necessary Razor" is a descending interrogation: Is it possible to ship without it? Really? Actually impossible? What if we did ship without it? Okay, cut it. More profoundly, Sylvester formalized **"apophenia design"** — a 2×2 matrix crossing "present/absent in game" against "perceived/not perceived by player." The goal is maximizing the cell where features are absent but perceived — players imagine the simulation is richer than it is. The practical technique: use abstracted feedback and long-term relevance to trigger pattern-recognition in the player's mind without implementing the underlying system.

## The Machinations workflow and the remove-and-compare test

Joris Dormans' Machinations framework, documented in his PhD thesis "Engineering Emergence" and the book *Game Mechanics: Advanced Game Design* (with Ernest Adams), provides the most rigorous documented process for distinguishing load-bearing from decorative mechanics. The framework extends Petri nets with game-specific constructs: pools collect resources, sources create them, drains destroy them, converters transform types, and critically, **state connections** — dotted arrows showing how resource distributions modify flow rates — close the feedback loops that drive emergence.

The Machinations workflow has four phases. First, map the internal economy: identify all resources (tangible and abstract), their sources, drains, converters, and flows. Second, add state connections to close feedback loops and classify each loop as reinforcing or balancing. Third, simulate: define artificial players with scripted strategies and run thousands of automated sessions, charting resource quantities over time. Fourth, iterate: introduce balancing mechanisms for problematic dynamics and re-simulate.

The critical filtering procedure is the **remove-and-compare test**: for each suspect mechanic, remove it from the Machinations diagram and re-run simulations. If the distribution of outcomes across thousands of runs is statistically unchanged, the mechanic is decorative. If the distributions shift significantly, it's load-bearing. Dormans demonstrated this with the SimWar case study, modeling and balancing a game that had never been built purely through Machinations simulation. A mechanic is load-bearing if it participates in at least one feedback loop — removing it breaks a cycle in the diagram and fundamentally alters system dynamics. Decorative mechanics are linear flows or elements outside all feedback structures, appearing as dead-end branches not connected to any state-connection cycle.

Reinforcing this, Alexandre Mandryka's Mechanics Map tool provides a complementary diagnostic: diagram game elements as nodes with verb-labeled relation arrows, then look for four structural patterns. **Clusters** (highly connected elements) indicate the systemic center. **Loops** (closed circuits) indicate tight gameplay. **Dead ends** (incoming arrows only) halt gameplay flow — suspect unless deliberately terminal. **Chains** (one-in, one-out sequences) signal bloated design where middle elements may be unnecessary. Tynan Sylvester's dependency stack method operates similarly: draw all mechanic dependencies, then define core gameplay as what emerges from the irreducible mechanics at the bottom of the stack. "Remove everything that can be removed without making a game emotionally worthless, and what's left is core gameplay."

## Detecting and preventing simulation anti-patterns

Five failure modes are well-documented in the literature, each with specific detection methods that go beyond intuition.

**Runaway leaders** emerge from unchecked positive feedback. The mathematical signature is first-order: if progress R[t] ≈ C₁P[t] + C₀ (progress proportional to accumulated position), the system produces exponential divergence. Detection via Machinations: trace all reinforcing loops and check whether each has a corresponding balancing mechanism. Nat Levan's mathematical framework identifies specific repair levers — mass damping (large starting pools slow exponential effects), diminishing returns (Power Grid's income curve), increasing costs (triangular number pricing), value caps, conservation mechanics (gaining rate-of-progress requires sacrificing current progress), and ending the game at the tipping point before feedback dominates.

**Poverty traps** are the symmetric failure. Ernest Adams' documented analysis defines the downward spiral as "positive feedback in the downward direction." The diagnostic: is the feedback self-reinforcing (losing makes losing more likely), zero-sum (one agent's loss directly empowers another), AND compounding (rate of loss accelerates)? If all three hold, you have a death spiral. Solutions break any one property — guaranteed minimum income, decoupling victory from the feedback variable, avoiding zero-sum resource transfers, or ensuring damage doesn't increase the probability of further damage.

**Behavior extinction** — mechanics becoming unused as the simulation evolves — maps directly to Daniel Cook's "skill atom burnout" concept. Cook's Chemistry of Game Design provides a measurable framework: each mechanic is a skill atom (action → simulation → feedback → mental model update) that "burns out" when fully mastered. If a burned-out atom doesn't chain into a new one, it's dead. The detection method is empirical: **"Hook up logging and observe where atoms light up and where they burn out."** In a simulation context, track which actions agents actually perform over time. Declining usage curves reveal behavioral extinction. Mechanics Maps flag this structurally: elements with only incoming arrows and no outgoing arrows are dead ends.

**State space collapse** — convergence to few stable states regardless of initial conditions — requires running many simulations from randomized starting conditions and measuring outcome variance. If variance decreases over simulation time, the system is collapsing toward attractors. From dynamical systems theory, this occurs when the game's mathematical structure has few attractors with large basins. The Machinations simulation framework directly supports this test.

**Dominant strategies** — the behavior space collapsing to one optimal path — have a documented taxonomy: memorizing (predictable patterns), turtling (passive strategy without punishment), and grinding (low-risk repetitive progress). Jesse Schell's Lens #32 provides the core diagnostic: **"If you have 10 cars but 1 is clearly better, it's like no choice at all. When you discover you have a dominant strategy, you should work to correct it."** Soren Johnson's solution in Old World was structural: card-draw tech selection introduces controlled randomness that prevents optimal-path-following, which deterministic tech trees inevitably produce.

## Architecture selection and the tool landscape

For a procedural history simulation with many goal-oriented agents, the documented professional consensus points toward a **Utility AI + HTN hybrid** as the optimal architecture, with formal specification as a verification layer.

Dave Mark's Infinite Axis Utility System (IAUS), deployed at scale in Guild Wars 2, provides the decision layer. Each agent scores all available behaviors via mathematical response curves mapping world-state variables to 0–1 scores. Constraints are embedded as considerations that return zero (hard veto) or asymptotically approach zero (soft constraint). The multiplicative composition means any single zero-scoring consideration kills a behavior's score — a natural AND-gate. **Behavioral diversity emerges automatically**: weighted random selection among top-scoring candidates (rather than pure argmax) prevents population homogeneity, and per-agent personality offsets create variation from identical logic. The IAUS design tool (also available via Mike Lewis' open-source Curvature AI) allows authoring new behavior packages in minutes through database-driven curve editing, with no code changes.

For complex multi-step agent plans — preparing for war, establishing trade routes, managing succession — GOAP or HTN planning supplements utility scoring. GOAP's precondition/effect system is inherently constraint-driven: actions only execute when all preconditions are satisfied, and practical implementations cap plan depth at 3–5 actions to prevent unbounded chains. HTN planning (used in Horizon Zero Dawn and prototyped for Elder Scrolls IV NPC scheduling via SHOP2) is strongest when behaviors decompose into natural hierarchies — "run a kingdom" decomposes into military/economic/diplomatic management, each decomposing further. The hybrid pattern: utility scores select the high-level goal, GOAP or HTN plans the execution sequence.

For prototyping and validation, the strongest documented toolchain combines **Machinations** for economy modeling, **Mesa** (Python ABM framework) for full agent simulation, and **TLA+** or **Alloy** for formal invariant verification. The ODD protocol (Overview, Design concepts, Details) from agent-based modeling provides the specification structure — forcing explicit documentation of emergence mechanisms, adaptation rules, agent objectives, sensing, interaction, and stochasticity before implementation. Pattern-Oriented Modeling (Grimm et al.) then validates: define target historical patterns the simulation should reproduce (rise and fall of civilizations, trade network formation, technological diffusion) and verify the model reproduces them simultaneously. Behaviors necessary for multi-pattern replication are load-bearing; those that aren't are candidates for removal.

## The synthesized six-phase workflow

The research converges on a specific process pipeline that addresses the user's core problem — getting from a large candidate action set to a coherent, verifiable design specification.

**Phase 1 (Invariants):** Define 10–15 simulation-wide invariants as formal predicates. No unbounded growth, conservation of key resources, no permanent monopoly states, populations bounded by carrying capacity. Express in TLA+-style notation or a custom DSL. This is where constraint-first design begins.

**Phase 2 (Stock-and-flow model):** Build a Machinations or system dynamics model of all resource types, flows, sources, and drains. Verify that the flow structure enforces Phase 1 invariants. Simulate to check for unbounded behavior, depletion, or oscillation.

**Phase 3 (Action derivation):** Map each flow to one or more agent action types using the Macal/Borshchev SD-to-ABM translation. Flow rate constraints become action frequency constraints. Stock bounds become population-level invariants. **Any candidate action that has no corresponding flow is structurally decorative — cut it.**

**Phase 4 (Feedback verification):** For each remaining action, verify it participates in at least one feedback loop using the Machinations remove-and-compare test. Run thousands of simulations with and without each mechanic. If outcome distributions don't shift, the mechanic is decorative. Apply the Mechanics Map diagnostic: look for dead ends and chains. Apply Cook's skill-chain analysis: does this action feed into subsequent actions, or does it burn out?

**Phase 5 (Anti-pattern sweep):** Run Monte Carlo simulations from varied initial conditions. Check for runaway leaders (exponential divergence), poverty traps (absorbing low states), state space collapse (declining outcome variance), behavior extinction (declining action usage over time), and dominant strategies (one strategy winning disproportionately). Apply documented repair mechanisms for each failure mode detected.

**Phase 6 (Formal verification):** Express the surviving action set as a TLA+ specification with Phase 1 invariants. Use the TLC model checker to exhaustively verify that no sequence of agent actions violates any invariant. Actions that can lead to invariant violations are either further constrained with guards or excluded. This is where the formal verification language the user mentioned comes in — but now they have a coherent specification to verify, derived from structure rather than intuition.

## Conclusion

The fundamental methodological insight across all documented sources is that **actions should be derived from structure, not filtered from a brainstorm list**. Wright derived SimCity's actions from Forrester's stock-and-flow formalism. Andersson derived Victoria 3's economy from named failure modes in Victoria 2. Fåhraeus derived CK2's character actions from the Opinion system's mechanical needs. Adams derives Dwarf Fortress features from target stories that require systemic prerequisites. In every case, the successful process is generative (structure → actions) rather than subtractive (brainstorm → filter).

The tooling to support this process exists today. Machinations handles economy modeling and the remove-and-compare test. The ODD protocol structures agent specification. Utility AI (via IAUS/Curvature AI) provides constraint-embedded decision architecture. TLA+ handles formal verification. Mesa enables rapid ABM prototyping. The missing piece has never been tools — it's the workflow inversion from "what actions sound cool" to "what flows does my resource structure require." Once that inversion is made, the action set becomes a derivation problem rather than a selection problem, and the candidate list shrinks from "everything we can imagine" to "everything the structure demands."
