**Decision** (recap): kernel is a pure tick-advancer with no loop, no clock, no rate awareness. A dedicated driver thread is the only caller. Consumers read from ring buffers off-thread. The audio-line semantics emerge from this; they aren't implemented by the kernel itself.

# Driver Boundary Spec

## Kernel surface (Engine.Kernel)

```csharp
public interface IKernel
{
    Tick CurrentTick { get; }
    WorldVersion CurrentVersion { get; }

    // Pure synchronous tick advancement. No clock, no sleep, no I/O.
    // Returns ticks actually advanced (may be < requested if a stop condition fires).
    int AdvanceTicks(int count, in AdvanceOptions opts = default);
}

public readonly struct AdvanceOptions
{
    public readonly StopPredicate? StopAt;   // optional fast-path early exit
    public readonly CancellationToken Cancel;
}
```

`StopPredicate` is `delegate bool(in KernelStopContext)` — a pre-allocated, no-capture function. The kernel checks it between ticks, never within a tick. Used for "advance until tick X" / "advance until pause-event observed."

The kernel is otherwise unaware of *why* it's being advanced.

## Driver surface (Engine.Host.Driver)

```csharp
public interface IKernelDriver : IDisposable
{
    DriverState State { get; }       // Stopped | Running | Draining
    Task RunAsync(CancellationToken ct);
    void RequestStop();
}
```

A driver owns:
- one thread (the sim writer thread)
- a pacing policy
- the sole reference to `IKernel.AdvanceTicks`

A driver does *not* own:
- consumer cursors (those live in `Engine.Eventing`)
- projection, UI, logging, telemetry
- knowledge of which events exist

Exactly one driver is active per kernel instance at a time.

## Driver implementations

### UnpacedDriver — MC, tests, batch

```
RunAsync:
    while (!ct && !stopRequested):
        advanced = kernel.AdvanceTicks(batchSize, opts);
        if (advanced < batchSize): break;       // stop condition fired
```

`batchSize` is tuning (typically 1k–64k). No sleep. No yield except cooperative cancellation. Saturates one core; consumers on others keep up via ring buffer.

### RealtimeDriver — interactive host

```
RunAsync:
    accumulator = 0
    last = monotonic_now()
    while (!ct && !stopRequested):
        now = monotonic_now()
        accumulator += (now - last) * config.TicksPerSecond
        last = now

        ticks = (int)accumulator
        if (ticks > config.MaxTicksPerSlice):
            ticks = config.MaxTicksPerSlice          // spiral-of-death guard
            accumulator = 0                           // drop debt; record overrun
        else:
            accumulator -= ticks

        if (ticks > 0):
            kernel.AdvanceTicks(ticks)

        sleep_until(last + config.SliceInterval)     // OS-precision yield
```

Config (host-owned, not kernel-owned):

```csharp
public sealed record RealtimeConfig(
    double TicksPerSecond,            // 1, 5, 10 today
    int    MaxTicksPerSlice,          // catch-up cap
    TimeSpan SliceInterval);          // wake granularity, e.g. 16ms
```

Pause/resume = stop driver / start driver. The kernel never sees a "paused" state.

### SteppedDriver — debugger, replay

```
StepOnce(int n):
    kernel.AdvanceTicks(n)
```

External signal advances; no loop of its own. Used by the debug UI's step button and by deterministic replay tools.

## Threading rules

| Thread | Allowed work |
|---|---|
| Sim writer (driver thread) | `AdvanceTicks`, `TryWrite` events |
| Consumer threads | Cursor reads, ID resolution, projection, formatting, I/O |
| UI thread | Reads projection results; *never* enters kernel |
| Worker pool | Planner snapshots, MC runs, batch analysis (each owns its own kernel for MC) |

Single-writer invariant: only the driver thread ever calls `AdvanceTicks` on a given kernel. Enforced by an analyzer + a debug-only thread-affinity assert in `AdvanceTicks`.

## Event flow under each driver

The event log is bounded and per-cursor. Consumer pacing never reaches the kernel:

```
Driver thread: AdvanceTicks → Emit → ring.TryWrite (bounded, may drop+count)
Consumer A (UI):       cursor_A.Read at UI cadence,    drops oldest on lag
Consumer B (trace):    cursor_B.Read at I/O cadence,   compacts on lag
Consumer C (telemetry):cursor_C.Read at batch cadence, blocks on its own buffer only
```

Under `UnpacedDriver`, ring overruns are likely and are a deliberate design point — slow consumers drop or compact per their own policy. Under `RealtimeDriver`, the ring is sized so steady-state consumption beats production at the configured rate.

## MC and tests

```csharp
// Test: deterministic, no driver thread needed.
var k = Kernel.New(seed);
k.AdvanceTicks(10_000);
Assert.That(...);

// MC: parallel runs, each its own kernel + driver.
Parallel.For(0, runs, i => {
    using var k = Kernel.New(seedBase + i);
    using var d = new UnpacedDriver(k, stopAt: TickReached(horizon));
    d.RunAsync(ct).Wait();
    exporter.Submit(k.Snapshot());     // consumer reads ring off-thread
});
```

Tests can call `AdvanceTicks` directly without a driver — the driver isn't a required abstraction, just the realtime/long-running one.

## What goes where

```
Engine.Kernel       IKernel, AdvanceTicks, AdvanceOptions, StopPredicate
Engine.Eventing     KernelEvent, ring buffer, cursors, schema (per prior doc)
Engine.Host.Driver  IKernelDriver, UnpacedDriver, RealtimeDriver, SteppedDriver,
                    RealtimeConfig, pacing math
Engine.Host         Composition: pick driver, wire consumers, lifecycle
Engine.Projection.* Consumers reading cursors
```

`Engine.Kernel` does not reference `Engine.Host.Driver`. The driver depends on the kernel, not vice versa.

## Invariants this preserves

- Kernel has no wall-clock, no rate, no sleep, no async, no consumer awareness.
- Single sim writer enforced at the driver layer.
- Consumers cannot stall ticks (ring buffer + independent cursors).
- Pacing policy is swappable without kernel changes.
- MC and tests pay no driver overhead.
- Real-time host gets correct isolation because the driver thread, not the UI loop, calls the kernel.

## What this rules out

- A `Tick()` method on the kernel that the UI calls per frame. (Couples kernel to UI cadence.)
- A kernel-owned background thread. (Kernel becomes stateful w.r.t. lifecycle; harder to test and MC.)
- Drivers that invoke consumers inline. (Re-introduces stalls.)
- Multiple drivers attached to one kernel. (Breaks single-writer.)


Input is the symmetric mirror of the event log: an inbound primitive stream, drained at tick boundaries, recorded for replay. Same schema discipline, opposite direction.

**Two distinct input channels — don't conflate them:**

| Channel | Affects | Goes where |
|---|---|---|
| Kernel commands | Sim state (toggle action, set policy, mutate attribute, issue order) | Command ring → drained at tick boundary by driver → kernel applies |
| Driver controls | Pacing only (rate, pause, single-step) | Driver config channel → driver loop reads at next iteration |

The player's "tune rate" goes through Driver controls and never touches the kernel. The player's "disable this NPC's combat action" goes through Kernel commands and is recorded for replay.

## Kernel command pipeline

```
UI / Network / AI script / Test
       │  TryEnqueue(cmd)
       ▼
   Command Ring (bounded MPSC)
       │
       ▼  (driver drains at start of tick)
Driver: foreach cmd in drained:
            kernel.ApplyCommand(in cmd)
            kernel emits CommandApplied or CommandRejected event
       │
       ▼
   Kernel runs the rest of the tick
       │
       ▼
   AdvanceTicks returns; events in log
```

`KernelCommand` is structurally identical to `KernelEvent` — same packed shape, same schema discipline, same generator:

```csharp
public readonly struct KernelCommand
{
    public ushort CommandType;
    public uint   CommandId;     // monotonic, assigned at enqueue
    public uint   IssueVersion;  // world version at issue, for staleness check
    public int    Int0..Int9;
    public float  Flt0..Flt1;
}

[KernelCommand(Id = 1, Name = "ToggleAction")]
public readonly partial struct ToggleActionCmd
{
    [Slot(0)] public required ActionScope Scope;     // Global | Faction | Entity
    [Slot(1)] public required int         ScopeId;
    [Slot(2)] public required ProcessId   Action;
    [Slot(3)] public required bool        Enabled;
}
```

Generator produces `submitter.TryEnqueue(in cmd)` and a view, exactly like events. Same registry, same `SemanticKind`, same versioning rules.

## Submission API — async + sync from the same primitive

```csharp
public interface ICommandSubmitter
{
    // Async: returns when written to ring. Result observed via event log
    // (CommandApplied/Rejected with matching CommandId).
    bool TryEnqueue<T>(in T cmd, out CommandHandle handle) where T : struct, IKernelCommand;
}

public readonly struct CommandHandle
{
    public readonly uint CommandId;
    public bool TryGetResult(out CommandResult r);    // non-blocking poll
    public ValueTask<CommandResult> WaitAsync(CancellationToken ct);  // sync mode
}
```

`WaitAsync` works because there's a completion table sized to outstanding commands; the kernel signals it after emitting the result event. The kernel itself doesn't know about `Task` — completion notification is a host-side detail wrapping the event stream.

**Async use** (UI, normal play): fire-and-forget; UI subscribes to result events for toasts / undo support.

**Sync use** (tests, turn-based, scripted scenarios):
```csharp
var (ok, h) = submitter.TryEnqueue(in cmd);
kernel.AdvanceTicks(1);
var result = await h.WaitAsync(ct);   // already complete — returns synchronously
```

In tests with no driver thread, you call `AdvanceTicks` directly; the command applies in that call, the result is ready when it returns.

## What the kernel sees

```csharp
// Internal kernel surface, called only by driver/AdvanceTicks
internal void DrainCommands()
{
    while (commandRing.TryRead(out var cmd))
    {
        if (cmd.IssueVersion != CurrentVersion && !IsVersionTolerant(cmd.CommandType)) {
            EmitRejected(cmd.CommandId, ReasonCode.StaleVersion);
            continue;
        }
        var ok = ApplyCommand(in cmd);   // dispatches by CommandType
        if (ok) EmitApplied(cmd.CommandId);
        else    EmitRejected(cmd.CommandId, lastReason);
    }
}
```

This runs as the first phase of every tick, before systems. Result: planner runs in tick T+1 with player toggles from tick T already visible. No string lookups, no validation strings — just `ReasonCodeId`s in the rejection event.

## Determinism and replay

- Ring drainage is FIFO; ties (multi-producer arrival) broken by `(SubmitterId, SeqNum)`.
- Every accepted command is recorded in the event log via `CommandApplied`. The log *is* the input record.
- Replay reads `CommandApplied` events from a recorded log, re-enqueues them at their tick, runs the kernel.
- This means commands are part of the deterministic input alongside seed and initial world. No separate "input file."

## Backpressure

`TryEnqueue` returns false when the ring is full. Same explicit-overflow rule as the event log. Submitters decide:
- UI: surface "action queued / dropped"
- Network: NAK upstream
- Tests: assert (this is a bug)

Ring is sized for steady-state burst tolerance; in `RealtimeDriver` it drains every tick so capacity matches max input/tick × ticks-per-slice.

## Driver controls (the other channel)

```csharp
public interface IDriverControl
{
    void SetTickRate(double ticksPerSecond);
    void RequestPause();
    void RequestResume();
    void RequestSingleStep(int n);   // valid only on SteppedDriver
}
```

These mutate driver state, not kernel state. Implemented as a tiny lock-free config struct the driver thread reads each loop iteration. No event log entry (or optionally a `DriverConfigChanged` event for telemetry — but the kernel never produces it, the host does).

## Project placement

```
Engine.Kernel       KernelCommand, internal DrainCommands, ApplyCommand dispatch
Engine.Eventing     CommandRing (MPSC bounded), command schemas + generator,
                    completion table for CommandHandle
Engine.Host         ICommandSubmitter wiring, IDriverControl, completion->Task bridge
Engine.UI / etc.    Builds typed commands, calls TryEnqueue
```

`Engine.Kernel` references neither `Task` nor the completion table — it just emits result events. The host turns those events into `Task` completions for sync callers.

## Invariants preserved

- Single sim writer: only the driver thread calls `AdvanceTicks`, which is the only thing that calls `DrainCommands`.
- No allocation in kernel: commands are value structs, ring is preallocated, dispatch is by `CommandType` switch.
- No strings: commands carry IDs and primitives; rejection reasons are `ReasonCodeId`.
- Bounded with explicit overflow: `TryEnqueue` returns false; counter increments.
- Replay: command stream is reconstructible from the event log alone.
- Sync and async: same `TryEnqueue` primitive; completion bridge gives `WaitAsync` for callers that want it.
